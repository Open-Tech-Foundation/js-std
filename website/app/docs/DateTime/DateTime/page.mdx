🕒 An immutable date and time in an IANA time zone.

<Callout type="info">
  Backed by the TC39 **Temporal** API where the runtime provides it, and by
  `Intl.DateTimeFormat` everywhere else. Both paths implement the same semantics, so
  behaviour does not change with the host. Time-zone support needs no bundled database
  and no dependency.
</Callout>

Months and days are **1-based** and `dayOfWeek` runs 1 (Monday) to 7 (Sunday), following
Temporal and ISO-8601 rather than the legacy `Date`. Every method returns a new instance;
nothing mutates.

## Syntax

```ts
import { DateTime } from '@opentf/std';

new DateTime(input?, options?);
```

## Parameters

| Name      | Type                                                        | Description                                                       |
| --------- | ----------------------------------------------------------- | ----------------------------------------------------------------- |
| `input`   | `string \| number \| Date \| DateTime \| DateTimeFields`     | ISO-8601 string, epoch milliseconds, `Date`, `DateTime` or fields. Omit for now. |
| `options` | `{ timeZone?: string, disambiguation?: Disambiguation }`      | `timeZone` defaults to `'UTC'`; `disambiguation` to `'compatible'`. |

Parsing is strict ISO-8601 — it throws a `RangeError` rather than yielding an
`Invalid Date`, because `Date.parse` is implementation-defined outside the ISO subset
and disagrees across runtimes.

```ts
new DateTime('2026-07-29');
new DateTime('2026-07-29T14:30:15.250');
new DateTime('2026-07-29T14:30:15+05:30');
new DateTime('2026-07-29T14:30:15+05:30[Asia/Kolkata]');
new DateTime(1785315615250);
new DateTime({ year: 2026, month: 7, day: 29 }, { timeZone: 'Asia/Kolkata' });
```

Units are `'year'`, `'month'`, `'week'`, `'day'`, `'hour'`, `'minute'`, `'second'` and
`'millisecond'`.

## Arithmetic

**Calendar units** (`years`, `months`, `weeks`, `days`) move the wall clock. **Exact
units** (`hours` and below) move the instant. Across a DST boundary the two differ:

```ts
const dt = new DateTime('2026-03-07T12:00:00', { timeZone: 'America/New_York' });

dt.add({ days: 1 }).format('HH:mm');  //=> '12:00'  — 23 real hours later
dt.add({ hours: 24 }).format('HH:mm'); //=> '13:00' — exactly 24 hours later
```

Month arithmetic clamps rather than rolling over:

```ts
new DateTime('2026-01-31').add({ months: 1 }).format('yyyy-MM-dd'); //=> '2026-02-28'
```

`diff` counts **whole** units for `year`, `month`, `week` and `day`, truncated toward
zero, and returns fractional elapsed time for `hour` and below.

## Time zones and DST

A wall-clock time can be missing or repeated at a DST transition. `disambiguation`
decides, matching Temporal:

```ts
const wall = '2026-03-08T02:30:00';           // never happens in New York
const timeZone = 'America/New_York';

new DateTime(wall, { timeZone }).format('HH:mm ZZ');
//=> '03:30 -04:00'  — 'compatible' shifts a gap forward

new DateTime(wall, { timeZone, disambiguation: 'earlier' }).format('HH:mm ZZ');
//=> '01:30 -05:00'

new DateTime(wall, { timeZone, disambiguation: 'reject' });
//=> throws RangeError
```

For an overlap — a wall time that happens twice — `'compatible'` takes the earlier
instant. `'reject'` throws in both cases.

## Format tokens

| Token | Output | | Token | Output |
| --- | --- | --- | --- | --- |
| `yyyy` `yy` | `2026` `26` | | `HH` `H` | hour, 0–23 |
| `MMMM` `MMM` `MM` `M` | `July` `Jul` `07` `7` | | `hh` `h` | hour, 1–12 |
| `dd` `d` | `29` `29` | | `mm` `m` | minute |
| `EEEE` `EEE` | `Wednesday` `Wed` | | `ss` `s` | second |
| `DDD` | day of year | | `SSS` | millisecond |
| `ww` | ISO week | | `a` | `AM` / `PM` |
| `zzz` | `Asia/Kolkata` | | `ZZ` `Z` | `+05:30` `+0530` |

Text in single quotes is literal. Only month and weekday names depend on `locale`;
everything else is locale-independent, so a pattern produces the same bytes on every
runtime — safe for filenames, log lines and database columns.

```ts
const dt = new DateTime('2026-07-29T14:30:15.250', { timeZone: 'Asia/Kolkata' });

dt.format("yyyy-MM-dd'T'HH:mm:ss");  //=> '2026-07-29T14:30:15'
dt.format('EEEE, d MMMM yyyy');      //=> 'Wednesday, 29 July 2026'
dt.format('MMMM', 'fr-FR');          //=> 'juillet'
dt.toISOString();                    //=> '2026-07-29T14:30:15.250+05:30[Asia/Kolkata]'
```

`toISOString` round-trips through the constructor exactly, and `toJSON` uses it, so
instances survive `JSON.stringify`.

## Compared with other date libraries

|                       | `@opentf/std`   | date-fns v4          | Luxon        | Day.js           | Moment          | js-joda            |
| --------------------- | --------------- | -------------------- | ------------ | ---------------- | --------------- | ------------------ |
| Paradigm              | immutable class | functions on `Date`  | immutable class | immutable wrapper | **mutable**  | immutable class    |
| Size, min + gzip      | **4.6 KB**      | ~1–15 KB, per import | ~20 KB       | 2 KB + plugins   | ~20 KB + locales | ~40 KB          |
| Tree-shakeable        | ❌ one class    | ✅ **best in class** | ❌           | via plugins      | ❌              | ❌                 |
| IANA time zones       | ✅ `Intl`       | ✅ `@date-fns/tz`    | ✅ `Intl`    | ✅ tz plugin     | ✅ moment-timezone | ✅ `@js-joda/timezone` |
| Bundles a tz database | **no**          | no                   | no           | no               | **yes**         | **yes**            |
| Runtime dependencies  | **zero**        | zero                 | zero         | zero             | zero            | separate packages  |
| Temporal precision    | ✅ where available | ❌               | ❌           | ❌               | ❌              | ❌ own model       |
| Strict parsing        | ✅ throws       | ✅                   | ✅           | ❌ loose         | ❌ loose        | ✅                 |
| Invalid input yields  | throws          | `Invalid Date`       | invalid object | invalid object | invalid object  | throws             |
| Locales               | `Intl`          | ~200 bundled modules | `Intl`       | bundled files    | bundled files   | separate package   |
| Status                | new             | active               | active       | active           | **maintenance** | active             |

The `@opentf/std` figure is measured, not estimated: `import { DateTime } from '@opentf/std'`
bundled with esbuild against a real install, minified and gzipped. The other columns are the
sizes those projects publish for themselves.

<Callout type="info">
  Closest in spirit to **Luxon** — an immutable class with `Intl`-backed zones and no
  bundled database — but with a much smaller API and Temporal precision where the runtime
  offers it.
</Callout>

**Where this wins.** Real IANA time-zone support with zero dependencies and no bundled
database. Temporal precision, which no other library in the table has. Strict parsing that
throws instead of handing back an invalid object that propagates silently. And it is
already installed if you use `@opentf/std`.

**Where it does not.** `DateTime` is one class, so it cannot be tree-shaken the way
date-fns can — importing it costs the full 4.6 KB even if you only format. date-fns also
ships far more functions, including business-day maths and dozens of `differenceIn*`
variants. Luxon and date-fns have absorbed a decade of DST and calendar bug reports;
this is new. And there is no `Duration` or `Interval` type yet, so `diff` returns a plain
number.

If bundle size dominates your decision, use date-fns. If you already depend on
`@opentf/std` and want correct dates without another package, use this.

## Runtime support

The whole API works on every runtime. Only the machinery underneath changes.

| Runtime | Backend |
| --- | --- |
| Node.js 26+, Deno, ES-Runtime | Temporal |
| Chrome 144+, Edge 144+, Firefox 139+ | Temporal |
| Node.js 24 / 25 with `--harmony-temporal` | Temporal |
| Node.js 22 and earlier, Bun, LLRT, Safari | `Intl` |

<Callout type="warning">
  `toTemporal` and `DateTime.fromTemporal` are the only members that need Temporal, and
  they throw where it is absent. Check `DateTime.hasTemporal` first.

  On **LLRT**, `Intl` ignores locales and component options, so month names, weekday
  names and `toLocaleString` do not work. Numeric tokens and all date arithmetic are
  unaffected.
</Callout>
